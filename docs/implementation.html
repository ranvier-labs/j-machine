Implementation note · 28 August 2026

J-Machine / MDP

A clean-room, synthesizable SystemVerilog reconstruction of the Message-Driven Processor, its queues, and its three-dimensional network—paired with an independent oracle, a compiler, and an FPGA platform target.

Architectural contract: MDP Architecture Version 11 · 36-bit tagged words · 17-bit instructions · X–Y–Z mesh routing

How standalone is it?

Standalone as an implementation; platform-bound as a finished machine.

The processor, queues, network endpoint, routers, mesh, golden model, compiler, simulation adapters, tests, and AWS F2 wrapper all live in this directory. The reusable RTL does not reach into a sibling repository. A running system still needs a memory binding, a loader, and either a simulator or an FPGA shell.

The clean boundary is j_machine_mesh. It exposes one processor word port and one four-word queue-row port per node. That keeps architectural state and message semantics inside the design while memory technology stays outside it. The same mesh can therefore sit behind dense simulation arrays, sparse DPI memory, or the F2 PCIM adapter without changing the processor.

Implementation

The implementation follows the published Version 11 encodings rather than translating them into a smaller convenience ISA. j_machine_pkg.sv is the contract: sixteen word tags, the published opcode and fault maps, 20-bit physical addresses, 17-bit packed instructions, and the two-priority network types.

One node. A router beside each node connects the message path to six spatial neighbors and the local port.

Processor

j_mdp_core.sv fetches two packed instructions per word and implements tagged operations, three execution contexts, priority preemption, fault vectors, base/limit addressing, translation, and message-send instructions.

Message unit

mdp_message_unit.sv owns both priority queues, queue head/base/limit state, four-word receive buffering, circular allocation, queue-full signaling, dispatch, and suspend handoff.

Network endpoint

The input side reassembles two 18-bit flits into a tagged word. The output side assembles messages in an eight-word FIFO, emits route headers, and preserves tail and priority semantics under backpressure.

Router and mesh

Each seven-port router uses deterministic X–Y–Z routing, message-level locks, and two priority networks. j_machine_mesh.sv repeats node/router pairs over a parameterized 3-D grid.

Software path

jmc parses a documented C11 subset and emits target-neutral tagged-word images. It includes the runtime conventions for remote calls, futures, suspension, code distribution, and reclamation.

Independent check

The C++ golden model decodes the same image format independently of the RTL. Tests compare architectural results across separate event- and cycle-based executions.

Evidence in this checkout

The project’s confidence comes from several different checks, not from a single self-test:

  • A standalone golden suite covers encodings, arithmetic, tags, comparisons, and fault selection.
  • The RTL regression differentially checks 6,656 opcode/tag cases plus directed memory, control, translation, interrupt, queue, DRAM-error, and message paths.
  • Compiler examples are rebuilt into images and executed by both the golden model and Verilated RTL.
  • A sparse hierarchical target runs the concrete 8 × 8 × 8, 512-node mesh without allocating dense memory for every node.
  • The F2 adapter has focused PCIM, queue-backpressure, and bundle-layout tests; the OCL control wrapper is packaged, but none of this is equivalent to routed-hardware signoff.

The 28 August 2026 Bazel cutover audit passed all 99 compiler-generated image regressions in the golden and RTL models, including SEND backpressure recovery and the four-node historical workload. The repository-wide suite also covers the compiler, the full golden/RTL differential, floating point, and F2 adapter checks. All three explicit 512-node workloads passed. Base and concrete 512-node Verilator lint complete with known non-fatal unused-signal, unused-parameter, and constant unsigned-comparison warnings.

Build surfaces

The build has one entry point: Bazel. The smallest runnable slice is the oracle; the ordinary suite adds the pinned Lean compiler, Verilator, floating-point dependencies, and F2 adapter checks.

# Independent C++ model
bazel test //:golden_test

# Compiler, generated programs, golden model, RTL, FPU, and F2 adapters
bazel test //:tests
bazel build --config=rtl-lint //sim:j_machine_verilator_rtl

# Explicit 512-node workloads and AWS packaging
bazel test //:long_tests
bazel build //aws_f2:cl_bundle

The source itself is compact—about 1 MB across RTL, compiler, simulators, documentation, and platform files in this audit—but generated build products can be several gigabytes. A clean checkout is therefore much more portable than the current built working directory suggests.

What remains outside the claim

  • No cycle-exact comparison against a recovered original MDP simulator has been made.
  • Stateful opcode/addressing/fault-precedence coverage is directed but not exhaustive.
  • External DRAM refresh and ECC registers beyond the visible memory/error interface are not reconstructed.
  • The 9-bit physical channel, board timing, F2 routed DCP, host allocator/loader, and on-hardware bring-up remain platform work.
  • The C front end is intentionally bounded; it is not a complete ISO C implementation.

This makes the project a substantial, locally executable reconstruction with a disciplined hardware boundary—not a drop-in replica of a historical J-Machine board.
